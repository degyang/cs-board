# Mountain 交付角色与文档交接规范

## 1. 目的

近期唯一产品目标是：用户通过新 WebUI 创建 Task，系统生成六阶段可执行工作单，Codex 按 Skills 完成各阶段并最终产出可播放视频。

所有关键需求、接口、路径、限制、问题、实现结果和审核结论必须进入版本库文档并随对应 PR 跟踪。聊天只负责发送文档位置和启动命令，不承载唯一需求。

## 2. 角色边界

### 2.1 用户：产品使用者和最终验收者

用户负责真实制作输入和产品判断：

- 提供任务名称和真实视频文案；
- 选择或提供参考音频；
- 选择风格、音色、成片参数和执行策略；
- 在需要时触发或确认人工/Codex 制作；
- 观看图片、音频、阶段视频和最终视频，决定接受或重做；
- 对最终 WebUI 体验和视频效果验收。

用户不负责：补写接口字段、推断目录、手工修复 manifest、替开发者准备测试夹具、解释 CCF/CCB 之间的契约。

自动化测试可以使用明确标记的测试数据，但不得把测试数据冒充用户真实输入或最终视频验收。

### 2.2 PM/审核者：Codex 主代理

PM 负责：

- 维护目标、优先级、里程碑和角色边界；
- 把产品需求转成字段级、状态级、路径级执行文档；
- 保持 WebUI、API、CLI、Task Store、Artifacts 和 Skills 契约一致；
- 给 CCF/CCB 提供唯一需求文档、明确工作目录、分支、基线和门禁；
- 审核真实代码、测试、运行证据和成果，不以开发者自报代替审核；
- 记录通过、驳回、遗留缺口和下一指令；
- 控制合并顺序，完成联合门禁和最终端到端验收。

PM 不替用户虚构真实文案、风格偏好或最终效果结论。

### 2.3 CCF：前端工程师

CCF 只负责 `web-v2`、前端测试、浏览器证据和相关映射/报告文档：

- 严格实现原型表面和真实后端契约；
- 呈现 Task 输入、六阶段工作单、状态、指令、路径、成果、重做和继续操作；
- 所有业务数据来自真实 API，不使用 mock/localStorage 代替生产状态；
- 对缺失后端契约展示明确不可用状态并写入 gap，不伪保存、不猜字段；
- 不修改 Python 后端、Task Store 或 Pipeline。

### 2.4 CCB：后端/CLI 工程师

CCB 负责 `csboard`、`webapp`、`cli`、后端测试和相关契约/报告文档：

- 把用户输入原子保存成 Task 输入；
- 生成六阶段确定性工作单及输入、指令、输出目录和预期成果；
- 提供 WebUI 与 CLI 同源 DTO 和命令；
- 支持外部/Codex 产物导入、校验、接受、拒绝和重做；
- 保证状态、Artifact revision、失效传播、日志和诊断一致；
- 不修改 `web-v2` 页面或自行决定交互设计。

### 2.5 Codex 工作流执行者

Codex 运行时负责：

- 从 Task/Run 工作单读取 Skill、参数文件、指令文件和输出目录；
- 严格按工作单执行当前阶段，不从聊天猜路径或参数；
- 将产物写入候选目录，通过 import/validate/accept 命令进入 Artifact Store；
- 失败时保留证据并按 retry 工作单重做；
- 不修改产品代码来绕过工作流失败；
- 不把“文件生成了”当成阶段完成，必须通过领域校验。

## 3. 单轮指令文档模板

每个 CCF/CCB 切片必须有一个版本化执行文档或在执行台账中有独立编号，至少包含：

1. 指令编号、角色、工作目录、分支和已验收基线 commit；
2. 此切片对端到端主链的直接贡献；
3. 唯一范围和明确非范围；
4. 真实前置契约及所有相关文件路径；
5. 输入 DTO、输出 DTO、状态机、错误码和安全边界；
6. 文件/Artifact 的规范相对路径；
7. 必须通过的行为测试和真实运行证据；
8. 禁止模式扫描；
9. 完整门禁命令；
10. 实现提交和报告提交名称；
11. 报告落点和是否允许推送。

指令中不得使用“参考以前实现”“按原型做”“适当补充”“确保可用”等无法独立执行的表述。引用原型、接口或其他文档时必须给出仓库内精确路径和章节。

## 4. 文档交流流程

### 4.1 PM 下达

- PM 先完成缺口分析，再写执行文档。
- 聊天指令只包含工作目录、同步命令、执行文档路径/章节和回报要求。
- 已在文档中的需求不在聊天重复改写，避免出现两个版本。

### 4.2 工程师执行

- CCF/CCB 开工前完整阅读指定章节和直接引用的契约文档。
- 发现矛盾或缺失时，在执行文档末尾添加 `Questions / Contract Gaps`，停止受影响的小项；可以继续不受影响的工作。
- 不得用假数据、兼容别名、静默 fallback 或扩大范围消除契约问题。

### 4.3 工程师报告

完成后新增报告文件或在指定位置追加 `Actual Delivery Report`，必须包含：

- commits 和实际变更文件；
- DTO/路径/状态变化；
- 测试和真实运行命令的原始摘要；
- 生成证据、哈希和环境；
- 已知缺口及其影响；
- clean status。

“全部完成”“测试通过”或表格打勾不能替代以上证据。

### 4.4 PM 审核

- PM 从 commit 和工作树独立复现关键门禁。
- 审核结论写回执行文档：`ACCEPTED`、`CORRECTION REQUIRED` 或 `BLOCKED BY CONTRACT`。
- 纠偏只写未满足的可观察事实、修正范围和复验门禁，不重复整份需求。
- 通过后才下达下一切片；不得让同一缺陷跨多个切片滚动。

## 5. 前后端协作规则

- CCF 与 CCB 不直接依赖对方的 sibling worktree；共享信息只通过集成基线和版本化契约文档。
- 同一垂直切片先确定后端 DTO/状态，再由 CCF 接入；允许并行实现已经冻结的部分。
- CCB 不因前端原型字段存在就实现未经 PM 确认的领域语义。
- CCF 不因 API 暂缺就添加 mock 生产路径。
- 每个联合切片必须运行：后端全量测试、前端全量测试、前端 build、真实服务 contract checker 和一条浏览器行为证据。
- PR 以可验收的垂直能力组织；前后端提交可以独立审计，但在同一里程碑 PR 中统一跟踪。

## 6. 近期交付顺序

1. CCF 完成 WebUI 新建 Task 六 Tab 与当前真实输入保存。
2. CCB 完成 Task `execution_plan` 的领域契约和持久化。
3. PM 联合冻结“Task Execution Bundle / Stage Work Order”契约。
4. CCB 实现六阶段工作单、CLI/API 查询和外部产物 import/validate/accept/retry。
5. CCF 在任务工作台呈现每阶段输入参数、Skill 指令、输出路径、成果和人工控制。
6. 修订并实际运行六个阶段 Skills；`video-workflow` 只负责编排。
7. 用户从 WebUI 提供真实文案等输入；Codex 按工作单执行完整流程。
8. 用户验收中间成果和最终 `final.mp4`，问题回到对应 Stage 重做。

## 7. 完成定义

近期里程碑只有同时满足以下条件才完成：

- 用户可以从 WebUI 保存完整 Task 输入；
- Task 中存在六阶段可读取、可追踪的工作单；
- 每个工作单明确 Skill、输入、参数、指令、输出目录、预期 Artifact 和校验命令；
- Codex 不依赖隐含聊天上下文即可顺序执行六阶段；
- 图片等外部成果可回存、校验、接受和重做；
- WebUI 与 CLI 看到相同状态和成果；
- 最终生成可播放视频、final manifest 和质量验证结果；
- 用户完成最终体验与视频效果验收。
